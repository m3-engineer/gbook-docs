# Phase 3: SCMI binds, the CPUs get cpufreq (2026-11-03)

Attempt `2026-11-03-8`. Image `ca51a59382dff6c8`, kernel `#7` (2026-11-03 4:07 PM ET), commit `ca81e32`. Sources: the
netlog `dumps/firstboot/2026-11-03-netlog.txt` and the AP console log `dumps/firstboot/2026-11-03-ap.log` (both
gitignored).

## Why

Every boot up to attempt -7 ended with one deferred device: `firmware:scmi … supplier 17430000.mailbox not ready`,
then `arm-scmi: failed to setup channels` and `failed to setup channel for protocol:0x10`. The CPUs stayed at whatever
clocks the firmware left them on.
- `mailbox@17430000` is `qcom,x1e80100-cpucp-mbox`. Its driver is `QCOM_CPUCP_MBOX` (`drivers/mailbox/Kconfig:343`,
  `qcom-cpucp-mbox.c:205`), `=m` in defconfig (`arch/arm64/configs/defconfig:1614`), and the initramfs loads no modules.
- **The stock tree drives the same block:** `cpucp: qcom,cpucp@18830000` (`qcom,cpucp-v2`) with the same two register
  ranges (`0x17430000`, `0x18830000`), an `arm,scmi` node with `mboxes = <cpucp 0 cpucp 2>` and shmem in
  `mmio-sram@18b4e000` (`entry00-base.dts:384-402`, `:908-926`, `:10534-10540`). `hamoa.dtsi` describes the same, and
  each CPU takes its `perf` domain from `scmi_dvfs` (`hamoa.dtsi:78-79`). So no DTS change. The stock tree also lists a
  vendor `protocol@80` that `hamoa.dtsi` does not have.

## Changes (commit `ca81e32`)

- **`kernel/mica-scmi.config`:** `QCOM_CPUCP_MBOX=y`. It also checks that the mailbox, SCMI core, SCMI mailbox
  transport, SCMI perf domain and SCMI cpufreq options are `=y` after the merge (they were already).
- **`/init`:** one `cpufreq` line per policy (CPUs, driver, governor, current, min and max kHz) and an `scmi-dmesg`
  capture.

  proof.
- The failures grew worse from -9 to -11. *Inference:* each failed boot may leave the firmware in a worse state for
  the next warm reset (the research note's quirk hazard, [scmi-cpucp-timeouts.md](../research/scmi-cpucp-timeouts.md)).

**Procedure from now on:** power stock off fully before each attempt. `attempt.sh verify` prints that step,
`attempt.sh watch` shows the EC's `G3->S5` line for a cold start, and `/init` reports the firmware version as the
`scmi-fw` key so `compare` flags a warm-reset boot. `arm,max-rx-timeout-ms` is not needed for cold boots; it stays
an option if a warm boot must work (for example after a crash reboot).

## Update: what the trace cannot tell (2026-11-03, 10:20 PM ET)

The latency in the tables above runs from `scmi_xfer_begin` to `scmi_rx_done`, and `rx_done` is traced in the mailbox
interrupt's handler (`driver.c:1164` at `a804c57`), so it cannot separate a late CPUCP reply from an on-time reply whose
interrupt woke an idle AP CPU late. "The slow replies follow the AP's idle states" (-28) holds either way; which side is
slow is open. Sibi Sankar's "idle states" statement is about `PERF_LEVEL_GET` hard resets, not reply latency, so it does
not decide this (inference). The discriminator is `arm,no-completion-irq` with idle states on
(`dts/diag/scmi-no-completion-irq.dtsi`): polling skips the interrupt; `trace_report.py` times a polled reply from begin
to end. Stock wires the mailbox the same way (`qcom,cpucp-v2` at `0x17430000`/`0x18830000`, GIC SPI 28 level-high, no
PDC; SCMI channels 0 and 2, no `arm,max-rx-timeout-ms`), with a downstream mailbox driver.

## Update: what -29 shows and does not (2026-11-03, 10:28 PM ET)

Polling keeps one AP core spinning through the whole SCMI probe, and `cpuidle.off=1` (-28) keeps every core out of the
PSCI states, so both fast cases share one property: the SoC never reaches its deepest state during the probe. -29 shows
that the CPUCP answers within 0.1 ms while one AP core is awake; whether it also does when all cores sleep is untested.
Two readings fit: CPU 0 sleeps through an on-time IRQ (SPI 28 has no PDC pin) until a timer wakes it, or the CPUCP
defers its reply while the AP is in a deep state. The window-tracking lead favours the first (inference). Next A/B:
`domain_ss3` dropped from `system_pd` alone (`dts/diag/hamoa-no-system-ss3.dtsi`).

## Update: precision on the -32 loop (2026-11-03, 11:08 PM ET)

- `state=1` is not only the `ret` state: its enter callback is `psci_enter_domain_idle_state` (`cpuidle-psci.c:271` at
  `a804c57`), which can escalate to a cluster or system domain state when CPU 0 is the last CPU of its domain. The
  `cpu_idle` event cannot tell which was requested; `power:psci_domain_idle_enter`/`_exit` (`power.h:89`, `:96`) can.
- Each cycle spends ~20 µs inside the state and ~0 µs outside: a PSCI call that returns without holding the state.
  Two readings fit: the firmware refuses (or immediately ends) the state while an SCMI command is in flight, or
  something wakes the core that the kernel does not see as an interrupt. Not decided.
- Two IPIs ran on CPU 0 mid-stall (0.502444 s, 0.538444 s) and the mailbox interrupt still did not follow them:
  SGIs reached CPU 0 while the SCMI reply's SPI did not (or was not yet raised).
- No I2C or GENI events fall in 0.43-2.1 s on -32, so this boot cannot say whether other SPIs stall the same way.
- Next capture (one boot, no fragment): `cpuidle/state*/{usage,rejected,time}` per CPU (`rejected` exists,

## Update: precision and two dead ends for the next test (2026-11-04, 12:31 AM ET)

- **The rate claim was too strong.** 2 of 6 stalled boots without domain idle states, against 8 of 11 with them, is
  not a significant difference at these sample sizes (one-sided p about 0.14, inference). Read it as "may reduce the
  rate; the sample cannot tell", not as "cut it to 2 of 6".
- **The window held on the 2-timeout boot.** 2026-11-04-1 (2 timeouts, max 1019.2 ms) still came up fully: firmware
  `0x20000`, `quirk_perf_level_get_fc_force`, cpufreq on all three clusters (netlog, boot 2 of 3 in
  `2026-11-04-netlog.txt`).
- **When the loop starts (-32):** the request left at 0.434542 s and CPU 0's first loop exit came at 0.434606 s,
  64 µs later, about when the reply's interrupt would be asserted (polling replies take ~0.1 ms, -29). Mid-loop
  CPU 0 took two SGIs (IPIs) but not the SPI, and a PPI (`arch_timer`) released it. Reading (inference): a pending
  SPI for CPU 0 wakes the core from `ret` but is not delivered to its CPU interface; the core re-enters, is woken
  again every ~20 µs, until a PPI runs. It also fits the 1.2-2.0 s loop with no SCMI pending (another SPI) and
  -30's GENI I2C `-110` timeouts (that controller's interrupt is an SPI on CPU 0 too).
- **`irqaffinity=` cannot move SPI 28 off CPU 0:** `irq_affinity_setup()` always adds the boot CPU to the mask
  (`kernel/irq/irqdesc.c:36` at `a804c57`).
- **CPU 0 alone cannot lose `ret` by DT:** with no state for one CPU, `psci_idle_init_cpu()` returns `-ENODEV`
  (`cpuidle-psci.c:399-401`) and `psci_cpuidle_probe()` fails the whole driver (`:437-447`), which is
  `cpuidle.off=1` for every CPU. Isolating CPU 0 or the interrupt needs a kernel patch.
