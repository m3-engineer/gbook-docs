### Board data

WCN7850 matches board data by bus and board (`ath12k/wifi7/pci.c:135,159` at `a804c57`). The name it builds is
`bus=pci,vendor=17cb,device=1107,subsystem-vendor=105b,subsystem-device=e0ee,qmi-chip-id=2,qmi-board-id=255`
(`core.c:232-247`). `board-2.bin` in linux-firmware-atheros `20260916-1` has exactly that entry. It also has
`variant=DE01` and `DE02` entries, but those are only picked through an SMBIOS/ACPI variant, which a DT boot doesn't
have (`qmi.c:2973-2982`). A board-data miss would have aborted the probe before `wlan0` registered (`core.c:520-580`),
so the mica module uses the generic Foxconn `105b:e0ee` entry. The stock `bdwlan.*` files from `modem_a` are not
needed.

## First try refused: "No valid image detected"

The first stick boot of this image failed with "No valid image detected" on screen. A re-insert gave the same error.

- **What the firmware log showed:** every rescan printed `GptNextKernelEntry … s0 t0 p0`, `no more kernels` and
  `vb2api_load_kernel() = 0x100b2000`.
- **What was on the stick:** read back on the build host, KERN-A had priority 0, tries 0. The image had written 15/3.
- **Why a re-insert can't help:** vboot marks a partition it rejects as bad (`GPT_UPDATE_ENTRY_BAD`,
  `2load_kernel.c:743` at `firmware-bluey-16702.B` `34fbbe6`).
- **Why the reason is lost:** the log is a 128 KiB ring (`Read cbmem console: size=131064`). It was full of rescans
  and menu lines, and the first attempt's error line was gone.
- **Outcome:** the stick was rewritten with the same image (read-back identical), and the next boot worked.
- **Cause:** unknown. *Inference:* a transient USB read on the first try, since the bytes and the size (the FIT is
  58.9 MiB, against the 256 MiB `KERNEL_SIZE`) were identical both times. The runbook's failure playbook now says to
  read the log right after the first refusal and to rewrite the stick before retrying.

## Update 2026-11-03: the cause of the "No valid image" refusals

The inference above ("a transient USB read") was wrong. Attempt 2 was refused the same way on its first two power-ons.
The EC console logged `boot_keys: recovery` (`boot_keys_value=0x00000009`) before both refused boots in
`dumps/firstboot/2026-11-03-ec.log`, and not before either boot that worked.

The owner had powered on with the recovery keys, because the agent's instructions said so; runbook section 6 says
plain power-on. In recovery mode vboot scans the stick for a recovery kernel. The dev-signed kernel fails that check,
and the partition is marked bad (`GPT_UPDATE_ENTRY_BAD`, `cgptlib.c:155` at `34fbbe6`). On that power-on, the first
USB scan already showed `s0 t0 p0` (owner photo of the firmware log).

After a rewrite and a power-on with no keys held, the stick booted. Runbook section 6 step 3 now forbids the recovery
keys with the image stick in.
