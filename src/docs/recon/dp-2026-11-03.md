## Why

In attempt 2026-11-03-5 the DP chain had already bound: `msm_dpu` bound all three DP controllers (`ae90000`, `ae98000`,
`aea0000`), `card2-DP-1` and `card2-DP-2` existed, and the `aux_bridge … failed to acquire drm_bridge` error from
[usb-2026-11-02.md](usb-2026-11-02.md) was gone. Both DP connectors read `disconnected` because nothing was plugged in.
The kernel already builds in every link of the path (`a804c57` `.config`):
- `QCOM_PMIC_GLINK=y`, which builds `pmic_glink_altmode.o` (`drivers/soc/qcom/Makefile:14`)
- `TYPEC_MUX_PS883X=y` (retimers), `PHY_QCOM_QMP_COMBO=y`, `DRM_AUX_HPD_BRIDGE=y`

`pmic_glink_altmode.c` sets the mux and retimer (`typec_mux_set`, `typec_retimer_set`) and reports HPD through
`drm_aux_hpd_bridge_notify` (lines 196-377), so `TYPEC_DP_ALTMODE=m` plays no part. The DTS already matched the 9345:
`link-frequencies` on `mdss_dp0_out`/`dp1_out` as in `x1e80100-dell-xps13-9345.dts:891`, `:899`, and
`data-lanes = <0 1 2 3>` from `hamoa.dtsi:5714`, `:5803`. The test needed only a sink and a capture.

## Which port is which

Three readings put the 9345's side labels the other way round on mica:
1. **SuzyQ, left port:** typec `port0` sinks power (`source [sink]`), as in every earlier boot.
2. **Stick, right port:** typec `port1` sources power, and in [usb-2026-11-02.md](usb-2026-11-02.md) the stick
   enumerated on `usb_1_ss1`.
3. **Monitor, right port:** it came up as `DP-2`, its USB on `a800000.usb` (`usb_1_ss1`).

*Inference:* typec `portN` is pmic-glink `connector@N`, and `DP-2` is `mdss_dp1` (the second DP connector registered).
So `connector@0` (retimer on `i2c3`, `usb_1_ss0`, `mdss_dp0`) is the **left** port and `connector@1` (`i2c7`,
`usb_1_ss1`, `mdss_dp1`) the **right** one. DP working on the right port supports this directly: pmic_glink_altmode
indexes its ports by each connector's `reg` (`pmic_glink_altmode.c:597`, `:615`), so it programmed the `connector@1`
chain (`i2c7` retimer, `usb_1_ss1` PHY) for the right port. Had the index pointed at `connector@0`, the `i2c3` retimer
would have been set and `mdss_dp1` would not have linked (*inference* from the code path, not traced per message). The DTS comments now say so (`dts/x1e80100-google-mica.dts`); the DTB
itself is unchanged.

## The device-link warning

`qcom_pmic_glink pmic-glink: Failed to create device link (0x180) with supplier 5-0008 for /pmic-glink/connector@1`
appears on every boot. At `a804c57`:
- `0x180` is `DL_FLAG_SYNC_STATE_ONLY | DL_FLAG_INFERRED` (`include/linux/device.h:444-445`). fw_devlink makes the
  link from `fw_devlink_create_devlink()` (`drivers/base/core.c:2219-2245`).
- A sync-state-only link only orders `sync_state()` callbacks. `device_link_add()` returns `NULL` for one if the
  supplier is not yet registered with PM, or if the consumer has already probed.

*Inference, not traced further:* the `i2c7` retimer registered after `pmic-glink` had probed. Either way, DP and
SuperSpeed both work on `connector@1`, so the warning blocks nothing.
